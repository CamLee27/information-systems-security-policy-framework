# Future Improvements

These items were not completed as part of the original course project. They represent changes I would consider before adapting the framework for a real organization.

## 1. Simplify the Data-Classification Model

The original project included several classification levels.

A future revision could:

- Reduce the number of levels
- Define clearer examples for each level
- Assign handling, storage, transmission, and disposal requirements
- Define who can change a classification
- Add a formal review process

## 2. Modernize Authentication Requirements

A future revision could:

- Reassess fixed password-composition requirements
- Define stronger password-length expectations
- Add compromised-password screening
- Clarify multifactor-authentication requirements
- Establish secure account-recovery procedures
- Review account-lockout behavior for usability and denial-of-service risks

## 3. Create Risk-Based Patch Deadlines

Instead of requiring every update immediately, a future policy could define remediation deadlines based on:

- Vulnerability severity
- Exploitability
- Exposure
- Asset importance
- Available compensating controls
- Operational risk

## 4. Expand Encryption Requirements

The original project broadly required encryption.

A future revision could specify:

- Encryption at rest
- Encryption in transit
- Approved algorithms and protocols
- Key generation and storage
- Key rotation
- Certificate management
- Access to cryptographic keys
- Response to lost or compromised keys

## 5. Formalize Incident Response

The original project documented a basic incident-response lifecycle.

A future version could add:

- Incident categories and severity levels
- Defined response roles
- Escalation criteria
- Evidence-preservation procedures
- Communication requirements
- Regulatory and contractual reporting reviews
- Recovery objectives
- Post-incident reporting templates
- Tabletop exercises

## 6. Add a Formal Risk Register

A risk register could document:

- Asset or process
- Threat
- Vulnerability
- Likelihood
- Impact
- Existing controls
- Risk owner
- Planned treatment
- Review date
- Residual risk

## 7. Add Third-Party Risk Requirements

Because the fictional platform connects schools, drivers, and other partners, a future version could define:

- Security requirements for vendors and partners
- Contract language
- Incident-notification expectations
- Access restrictions
- Data-sharing rules
- Periodic security reviews
- Offboarding and access removal

## 8. Map Controls to a Recognized Framework

A future revision could map proposed controls to a recognized cybersecurity framework or control catalog.

The mapping would show:

- Which framework requirement each control supports
- Which controls are missing
- Which policies overlap
- Which controls need technical implementation or testing

## 9. Verify Regulatory Applicability

The original project discussed FERPA, accessibility, and health-information privacy.

A real implementation would require:

- Legal review
- Identification of applicable jurisdictions
- Review of the organization’s role and relationships
- Identification of regulated information
- Documentation of compliance responsibilities
- Ongoing review as services and data uses change

## 10. Test Control Effectiveness

The original project proposed controls but did not implement them.

Future testing could include:

- Access-control reviews
- Vulnerability scans
- Backup-restoration tests
- Incident-response exercises
- Log-review testing
- Phishing simulations
- Firewall-rule reviews
- Privileged-account audits
- Third-party access reviews

## 11. Improve the Architecture Diagrams

The original diagrams are useful conceptual artifacts.

A future version could separate them into:

- Stakeholder diagram
- Data-flow diagram
- Application architecture
- Trust boundaries
- Network zones
- Data stores
- Authentication flow
- Administrative access flow

## 12. Add Policy Administration Details

Each policy could include:

- Policy owner
- Approval authority
- Effective date
- Review frequency
- Exceptions process
- Enforcement
- Related standards
- Related procedures
- Version history
